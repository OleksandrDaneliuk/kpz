## 1. Аналіз за методологією QOC (Questions, Options, Criteria)

### Question 1: Як розподілити відповідальність за розрахунок вартості та управління станом бронювання?
* **Option 1.1**: Залишити розрахунки в процедурному сервісі (`BookingCalculatorService`), зобразивши класи як DTO з get/set.
* **Option 1.2**: Перенести розрахунки безпосередньо в доменні моделі `Booking`, `Room`, `Season` (Rich Domain Model).
* **Criteria**:
  * *C1: Інкапсуляція та цілісність даних.*
  * *C2: Повторне використання логіки (Reusability).*
  * *C3: Тестованість без залучення моків (Unit Testing).*

> **Оцінка за QOC**: Option 1.2 перемагає за всіма критеріями. `Booking` містить необхідну інформацію для обчислення фінальної суми (Information Expert).

---

### Question 2: Як відокремити побічні ефекти (БД, SMS, UI) від доменної логіки?
* **Option 2.1**: Прямий виклик рішень збереження та сповіщень з доменного сервісу.
* **Option 2.2**: Використання паттернів **Pure Fabrication** та **Indirection** (абстракції `BookingRepository`, `NotificationService`).
* **Criteria**:
  * *C1: Low Coupling (Слабке зчеплення).*
  * *C2: Дотримання принципу Single Responsibility (SRP).*
  * *C3: Легкість підключення нових каналів сповіщення/БД.*

> **Оцінка за QOC**: Option 2.2 забезпечує високу гнучкість та можливість замінити реалізацію БД або SMS без дотику до бізнес-правил.

---

### Question 3: Як обробити варіанти тарифів послуг та сезонних коефіцієнтів?
* **Option 3.1**: Ланцюжки `if-else` / `switch` за текстовими стрічками.
* **Option 3.2**: Застосування Строготипізованих Enum з власною поведінкою (`Season`, `ExtraService`).
* **Criteria**:
  * *C1: Type Safety (Типобезпека).*
  * *C2: Protected Variations (Захист від змін).*

> **Оцінка за QOC**: Option 3.2 повністю усуває магічні стрічки та числа, захищаючи код від недійсних значень на етапі компіляції.

## 2. Обґрунтування рішень за принципами GRASP

| Принцип GRASP | Застосування в рефакторингу |
| :--- | :--- |
| **Information Expert** | **`Booking`** обчислює підсумкову вартість проживання та податки, оскільки володіє посиланнями на кімнату, кількість ночей, обрані послуги та сезон. **`Season`** знає свій коефіцієнт. |
| **Creator** | **`BookingService`** або фабричний метод у **`Booking`** відповідає за створення нового екземпляра бронювання із валідацією початкового стану. |
| **Controller** | **`BookingConsoleController`** виступає першою точкою входу для UI: зчитує введення користувача, викликає application service та відображає результат. |
| **Low Coupling** | Класи домену більше не залежать від `Scanner`, `System.out`, файлів чи SMS. Інфраструктура винесена за інтерфейси. |
| **High Cohesion** | `Booking` відповідає тільки за стан бронювання. `NotificationService` — за відправку сповіщень. `BookingRepository` — за збереження. |
| **Pure Fabrication** | Інтерфейси `BookingRepository` та `NotificationService` створені штучно для збереження чистоти домену та послаблення зчеплення. |
| **Indirection** | Шар application-сервісів (`BookingApplicationService`) слугує проміжним шаром між UI та доменом/інфраструктурою. |
| **Polymorphism / Protected Variations** | Застосування `Enum` для сезонів та послуг дозволяє легко додавати нові тарифні сітки або типи послуг без зміни коду розрахунку. |

## 3. Наслідки (Consequences)

### Позитивні
* **Rich Domain Model**: Доменні класи інкапсулюють свої дані та бізнес-правила, унеможливлюючи створення об'єкта в невалідному стані.
* **Тестованість (Testability)**: Бізнес-логіку розрахунку цін і податків можна покрити швидкими Unit-тестами без запуску консолі чи налаштування БД.
* **Гнучкість (Maintainability)**: Зміна способу сповіщення (наприклад, перехід на Email) вимагає лише створення нової реалізації інтерфейсу `NotificationService`.

### Негативні / Ризики
* Збільшення кількості файлів та класів у проєкті через введення інтерфейсів та шарів Clean Architecture.
